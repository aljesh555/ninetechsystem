## Stack and build

**Astro 7, static output, vanilla CSS, no UI framework.** As specified (built on
Astro 5; upgraded to 7 in September 2026 to clear security advisories in Astro and
sharp — the built pages were compared before and after and are equivalent). Nothing
in the site needed a component runtime, so no JavaScript framework ships at all.
Total JS on the heaviest page is 15 KB of hand-written inline script.

**The whole stylesheet is inlined into every page** (`build.inlineStylesheets:
'always'`). The CSS is 18.6 KB raw, about 5 KB gzipped. Inlining removes the only
render-blocking request on the page and satisfies "critical CSS inlined". The
cost — re-downloading it with each HTML document — is real but small, and HTML is
served `must-revalidate` anyway. This is the single biggest reason LCP is 1.4s on
throttled mobile.

**`build.format: 'file'`, `trailingSlash: 'never'`.** Emits `/services.html`,
which Cloudflare Pages serves at `/services` and 308-redirects `/services/` to.
One URL form, no duplicate-content canonicalisation needed. Verified locally.

**`scripts/serve.mjs` replaces `wrangler pages dev` for local testing.** Wrangler's
dev server produced no output in this non-interactive shell and could not be
driven. The replacement mimics the three behaviours that matter — clean URLs,
the trailing-slash redirect, and the rules in `_headers` — and also mounts the
contact Function, so the form was testable end to end. It is a development tool
and is not deployed.

## Typography and fonts

**Four `woff2` files, 33.7 KB total**, against a budget of four files and 120 KB.

| File | Contents | Size |
|---|---|---|
| `inter-400-500.woff2` | Inter, weights 400–500 | 12.5 KB |
| `poppins-600.woff2` | Poppins SemiBold, Latin | 4.7 KB |
| `poppins-700.woff2` | Poppins Bold, Latin | 4.6 KB |
| `poppins-500-devanagari.woff2` | Poppins Devanagari | 12.0 KB |

**Inter is shipped as a variable font pinned to 400–500.** Google Fonts serves
Inter's Latin slice as a single variable file — the CSS returns the *same* URL
for weight 400 and weight 500. Pinning the `wght` axis to `400:500` with
`fonttools varLib.instancer` and then subsetting gives one 12.5 KB file covering
both weights, instead of two static files. That freed a slot in the four-file
budget, which is why Poppins 700 is affordable for the hero display line.

**Latin faces are subset to the characters actually used** — ASCII plus `é`
(cafés), the dashes, curly quotes and ellipsis. Google's own `latin` subset
carries accented characters this site never sets.

**The Devanagari face is subset to the two Nepali strings, character for
character**, with all layout features kept so conjuncts render (टेक्नोलोजी,
चाहनुहुन्छ both verified in the browser). 12 KB for two lines is more than it
sounds, but Devanagari shaping tables are the cost of rendering Nepali correctly,
and the alternative — an image of text, or no Nepali — is worse.

Both families are SIL Open Font License 1.1, which permits commercial use and
self-hosting. The licence is committed at `public/fonts/OFL.txt`.

Regenerate with `python3 scripts/build-fonts.py`.

| `logo-symbol-white.svg` | The mark on the share card |
| `logo-symbol-navy.svg` | Recoloured to `logo-symbol-mono.svg` for empty image slots |

*(File names were updated after review; earlier drafts of this document used the
short names from the first delivery, such as `symbol-navy-square.svg`.)*

The palette in the supplied files matches the brand system exactly — `#123566`,
`#FF9500`, `#5A6B82`, plus `#9FB0C4` for "TECHNOLOGY" on dark grounds. Nothing
had to be recoloured.

**Four things had to be fixed before the files could ship:**

1. **The C2PA "content credentials" manifest was stripped.** Every file carried
   an 8–12 KB base64 metadata block — roughly three quarters of the file — with
   tool and document identifiers in it. It is dead weight on a file that gets
   inlined into the HTML, and it is provenance data that does not need to be
   served to the public.

2. **`wordmark-white.svg` had an opaque navy background rectangle** spanning the
   whole canvas. Inlined as delivered, it paints a `#123566` box wherever the
   logo sits — plainly visible against the footer's deeper `#0E2A52`. The rect is
   removed by exact match, so a future file without it is left alone and one with
   a different backdrop warns rather than silently mangling the art.

3. **The wordmark viewBox was cropped to the artwork.** As delivered it carried
   about 20% empty margin, which would have made the header logo look undersized
   for no reason. Measured by rendering and trimming: the ink is 2.363:1, the
   delivered box was 1.811:1. New viewBox `91 88 608 259`, verified not to clip —
   ink measures 597×253 inside a 600×256 render.

4. **svgo, at one decimal place.** The artwork is auto-traced: the 9 alone was
   189 path commands with 1,072 two-decimal numbers. Since these files are
   inlined into every page, the saving is real page weight:

   | File | Delivered | Shipped |
   |---|---|---|
   | `wordmark-navy.svg` | 12.1 KB | 2.1 KB |
   | `wordmark-white.svg` | 12.1 KB | 2.1 KB |
   | `symbol-navy-square.svg` | 15.8 KB | 3.2 KB |
   | `symbol-navy` / `-white` / `-mono` | 15.7 KB each | 3.2 KB each |

   Fills, viewBox and the accessibility attributes are excluded from
   optimisation, because those are load-bearing.

**The share card was rebuilt** (`scripts/build-og.py`) from `wordmark-white.svg`
for the name and `symbol-white.svg` as a 16%-opacity graphic on the right. Only
the tagline and strapline are still drawn from outlined Poppins. The instruction
named `symbol-white.svg` for the card; the wordmark is there too, because a share
card without the company's name on it is a weaker card.

**The favicon set comes from `symbol-navy-square.svg`** — it is the only square
lockup, and the only one that survives 32px. Checked at 32px upscaled: the ring
and stem still read. Output is `favicon.svg`, `favicon-32.png`,
`apple-touch-icon-180.png`, `icon-192.png`, `icon-512.png` and
`manifest.webmanifest`.

**Retired:** `scripts/build-logo.py` and the wordmark it generated. The in-code
mark existed only because `assets/brand/` was empty at the start; the real mark
is a geometric 9 built from a ring and two stems, not the Poppins numeral I had
approximated.

## The static map

**OpenStreetMap tiles, fetched once, stitched and committed** —
`scripts/build-map.mjs`, zoom 17, 1200×675, centred on 27.724562, 85.322562, with
a brand-coloured marker drawn over it.

- *Why not a Google Static Maps image:* it needs an API key, a billing account,
  and a per-request call at page load.
- *Why not an iframe:* the brief forbids it, and it would cost several hundred KB
  of third-party JavaScript on the page the site most wants people to reach.
- *Why zoom 17 rather than 16:* at 16 the street names are illegible once the
  image is displayed at ~520 CSS px. At 17, "Lazimpat Road", the Indian Embassy
  and Hotel Shangri-La are all readable, which is what makes a map useful.
- *Licensing:* OSM tiles are ODbL. Commercial use is permitted with attribution,
  which appears both burnt into the image and as a caption beneath it. The tiles
  are fetched **once** and committed, not on every build, so no load is placed on
  OSM's servers. The script is deliberately not part of `npm run build`.

Astro's image pipeline turns the committed PNG into AVIF and WebP at 400/800/1200w.
Largest variant is 77 KB, under the 150 KB ceiling.

## The contact form

**Resend, via a Cloudflare Pages Function.** MailChannels withdrew free sending
for Cloudflare Workers on 31 August 2024, and Cloudflare's own documentation now
points at Resend. Free tier is 100 emails/day and 3,000/month, far beyond what a
five-page site's enquiry form will produce.
Sources: [Cloudflare's Resend tutorial](https://developers.cloudflare.com/workers/tutorials/send-emails-with-resend/),
[MailChannels' withdrawal](https://en.wikipedia.org/wiki/MailChannels).

Requires `RESEND_API_KEY` as a Pages secret and a verified sending domain. Both
steps are in `DEPLOY.md`. **Until the key is set, the form returns a clear error
telling the visitor to call or WhatsApp instead** — it never pretends to have
sent something it did not send.

**Defences, in order:** same-site `Origin` check → honeypot field → timing check
(under 3 seconds or over 24 hours is rejected) → server-side validation of every
field with length caps → per-IP rate limit of 5/hour.

**The rate limit needs a KV namespace bound as `RATE_LIMIT`.** The code uses it if
it is bound and skips it if it is not, so the form works either way;
`DEPLOY.md` covers both creating the namespace and the dashboard rate-limiting
rule that serves as the alternative.

**Nothing is stored.** No database, no repo file, no log of submissions. The
message is emailed to info@ninetechsystem.com and forgotten.

**The form works without JavaScript.** A plain form POST gets a real HTML
confirmation page back rather than raw JSON. The timing check is skipped in that
case (there is no client to set the timestamp) and the honeypot carries the load.

32 automated tests cover all of this: `node scripts/test-contact.mjs`.

**Revised after review: the page and the server must agree, and the visitor must
be told the real reason.** The first version checked the phone number more
loosely in the browser than on the server, and whatever the server said, the page
showed "That did not send, please call us". A visitor who typed `984.332.5804` was
told the site was broken. Now:

- the phone rule (`PHONE_CHARS`) and the 3-second minimum (`MIN_FILL_MS`) are
  exported from `functions/api/contact.js` and handed to the page, so there is one
  definition;
- every JSON error carries a `message` written for the visitor, and a 422 lists
  the `fields` to fix, which the page marks;
- someone using autofill can finish inside 3 seconds, so the page waits out the
  remainder before sending instead of letting the server reject a real person;
- the honeypot was called `website`, a name browsers and password managers
  sometimes autofill — which would have silently binned a real enquiry while
  showing "Message sent". It is now `extra`, labelled "Leave this empty";
- the Origin check allowed *any* `*.pages.dev` site, which anyone can create for
  free. It now allows only `ninetechsystem.pages.dev` and its preview subdomains;
- a malformed body (`null`, an array, broken JSON) and an unreachable mail
  provider return clean 400 / 502 responses instead of throwing;
- the business types, phone number and recipient address come from
  `src/data/site.js`, not copies inside the Function.

## Security

**A strict CSP with no `'unsafe-inline'`.** Because the stylesheet and the scripts
are inlined, the usual shortcut would be `'unsafe-inline'` on both. Instead
`scripts/postbuild.mjs` hashes every inline `<style>` and `<script>` the build
emitted and writes them into the policy. This required avoiding `style="..."`
attributes throughout — verified: the build output contains none.

The policy also sets `frame-ancestors 'none'`, `base-uri 'none'`,
`object-src 'none'` and `form-action 'self'`.

**HSTS is deliberately not in `_headers`.** Cloudflare applies it at the edge, and
setting it in two places invites them to disagree. `DEPLOY.md` has the dashboard
step to confirm it is on.

**The email address is published plainly, as a normal `mailto:` link.** An
earlier build disguised it as `info [at] ninetechsystem.com`, but the same address
was already in plain text in the JSON-LD on every page and in `llms.txt`, so the
disguise protected nothing and only made it harder for people to use. The founder
decided it does not need hiding. It is a role address (`info@`), not a person's,
and spam is left to the mail provider's filter.

**`scripts/security-check.mjs` greps the build output** for registration numbers,
PAN/VAT, bank and merchant details, the internal tool stack, banned marketing
words, ranking guarantees and any phone number or email that is not the two
published ones. It runs clean. *Note:* its first run produced 27 false positives
(a partial match inside the `wa.me` URL, the AI crawler names in `robots.txt`, and
the FAQ sentence that **denies** ranking guarantees). The rules were tightened
rather than relaxed, so a future real hit will not be lost in noise.

## SEO, AEO and GEO

**Cloudflare now blocks AI crawlers by default on new domains — this is the single
most important post-deploy step.** As of 15 September 2026, Cloudflare blocks
crawlers classified as *Training* and *Agent* by default on new zones; *Search*
stays allowed. The controls are three independent presets (Search / Agent /
Training), available on every plan including Free.

The recommendation, with reasoning, is in `DEPLOY.md`: allow all three.
*Search* and *Agent* are non-negotiable — Agent covers the user-triggered fetches
that happen when somebody asks ChatGPT for a web developer in Kathmandu, which is
exactly the traffic this site is structured for. *Training* is allowed too: for a
five-page marketing site with no proprietary content, being in the training data
is upside, and there is nothing here worth withholding.

Without this, every answer-first paragraph, the `llms.txt` and the schema are
invisible to the engines they were written for.
Source: [Cloudflare on content control](https://blog.cloudflare.com/control-content-use-for-ai-training/).

**`llms.txt` is generated from `src/data/site.js`,** the same module the pages and
the JSON-LD read from. It cannot drift out of step with the site. (The care-plan
lines were hand-written at first; they are now generated from `carePlans` too.)

**The business is one JSON-LD entity, not two.** It was an `Organization` plus a
separate `ProfessionalService` that named the Organization as its own
`parentOrganization` — a company listed as its own parent. It is now a single
node typed `["Organization", "ProfessionalService"]` at `/#organization`, and
every Service, page and Person points there. `priceRange: "NPR"` was dropped: it
is a currency, not a price range, and there are no published prices.

**The sitemap carries no `<lastmod>`, `<priority>` or `<changefreq>`.** The build
stamped every page with the build date on every build, which teaches Google to
distrust the field; the other two are ignored by Google.

**The Home `<title>` is 65 characters, over the 60 the brief asks for.** The brief
also specifies that exact string. The specified string won, because the words that
would have to go are "Automation" or "Kathmandu" — the differentiator and the
local term. The important words are at the front, so truncation costs little. All
four other titles are within 60.

**No blog, no per-service landing pages, no keyword-stuffed titles.** As directed.
The local pattern of "Best Web Design Company in Nepal, Top Web Development…" is a
penalty pattern, not a strategy.

## Content

**`src/data/projects.js` is an empty array.** The Work page and the Home work
section render the honest empty state. The three placeholder entries the brief
asks for live in that file as commented templates, marked `PLACEHOLDER: replace
with a real project before publishing`, together with the permission and
anonymisation rules. They are **comments in source, not HTML comments in the
build** — shipping `<!-- PLACEHOLDER -->` to production would violate the rule
about not deploying build artefacts, and would be visible to anyone viewing
source. This is a deliberate deviation from the letter of §6.3.

**The service pages carry no fabricated proof of any kind** — no testimonials, no
logos, no invented statistics, no stock photography. Every image slot renders a
brand placeholder.

## Design decisions taken during the build

These changed after seeing the work in a browser. `DESIGN_PLAN.md` §6 records the
three revisions made before coding; these are the ones found afterwards.

**The amber full stop was rebuilt.** First implementation used an absolutely
positioned pseudo-element, which put the square in the descender space — it read
as a stray dot below the line rather than a period. It is now an inline-block
aligned to the baseline, which is exactly where a full stop sits. The real period
is kept beside it, screen-reader-only, so the text still reads and copies
correctly.

**The step numbers on About are grey, not amber.** Amber on off-white is 2.2:1 and
those numerals are content, not decoration. The plan's own rule — amber is never
text — had been broken. Fixed rather than excused.

**Empty image placeholders were made quiet, then hidden on mobile.** They started
as saturated navy blocks with a large 9, which competed with the copy beside them.
They are now off-white with a hairline border and a small mark. In the services
rail on phones they are hidden entirely: an empty decorative slot costs a phone
user a screenful of scrolling and tells them nothing. Structural slots (people,
office, work) always render.

**The focus ring is navy on light grounds and amber on navy grounds.** The plan
said "amber at 3:1 against both"; amber on white is 2.2:1, so that was wrong.
Navy on white is 9.6:1 and amber on navy is 5.9:1.

**The timeline sits beside each service's name, not in the detail grid.** It first
lived in a third grid column, which slid left whenever a service had nothing under
"Not included". When prices were removed the timeline moved into the price's slot
(see below) and the column was dropped.

**"How we work" on About is a `<details>` accordion.** Requested as a dropdown
FAQ. Built on native `<details>`/`<summary>`, so it opens without JavaScript, is
keyboard operable and is announced correctly by screen readers with no ARIA to
maintain. The first step is open on load so the section is not five closed bars.
The numbering stays: it is still a real sequence.

**The two directors show name and title only.** The one-line role descriptions
were removed at the founder's instruction, from the About page and from
`llms.txt`, which had them hard-coded and now reads them from `people`.

**The empty-state heading on `/work` is an `h2`, not an `h3`.** It follows the
`h1` directly, and Lighthouse caught the skipped level.

**The header uses the supplied full lockup, above 900px.** An earlier build
assembled the symbol next to the wordmark by hand, after comparing four
alignments in the browser. When the official `logo-full-navy.svg` arrived that
was thrown away — the spacing between mark and name is a brand decision, not
something to guess at. Three sizes were compared; 186px in a 96px bar is where
"TECHNOLOGY" stays legible without the bar starting to compete with the hero.
Below 900px the wordmark goes alone: the full lockup spends about a third of its
width on the 9, and on a phone the bar also carries the phone number, WhatsApp
and the menu.

**`logo-full-white.svg` arrived with the 9 still navy.** Everything else in the
file had been recoloured white, but the symbol path was missed, so on a navy
ground the mark all but disappeared — caught by reading the fill order (one
`#123566` against fourteen `#FFFFFF`) and confirmed by rendering it on the
footer's navy. `prepare-brand.mjs` recolours that single fill and logs that it
did; it warns if a future file has no navy fill to correct, or still has navy
left afterwards. Flagged to the founder to fix in the master file, since the
broken version would also go to a printer or sign-maker.

**The header bar is 96px on desktop, not 68px.** The supplied lockup is stacked
(2.35:1), so its *height* is the binding constraint. A 68px bar capped the logo
at 50px, which on a 1920px screen read as no logo at all. Sizing the bar to the
logo rather than the logo to the bar is the right way round.

## Prices removed at the founder's instruction

*Superseded in September 2026 by the services rebuild below, which publishes
prices. Kept for the record.*

Pricing had not been finalised, so publishing figures would have broken the
brief's own rule against publishing anything that cannot be stood behind. Every
"From NPR …" figure is gone — from the pages, the care-plan table, the FAQ
answers, `llms.txt`, the meta descriptions and the JSON-LD.

What replaced them:

- **The headline slot beside each service now holds the timeline.** The design's
  one designed object was the price, set as a menu-style right-aligned figure. It
  would have been a waste to delete the treatment, and the timeline is the next
  thing a buyer wants at a glance, so the `.price` class became `.fact` and holds
  "2–3 weeks", "Monthly", and so on. The Timeline column came out of the detail
  grid so the same fact is not stated twice.
- **`Service` schema carries no `offers`.** Publishing a price in structured data
  that the company has not committed to would be worse than publishing none.
- **The Services H1 changed** from "What we do, and what it costs" to "What we do,
  and how we quote it", because the old one promised something the page no longer
  delivers.
- **The cost FAQ was rewritten** to answer the question honestly — what moves the
  price, and that a written fixed price follows a free scoping call — instead of
  quoting numbers.

`README.md` has the steps to put prices back when they are settled.

## The services rebuild (September 2026)

Built from `SERVICES_REDESIGN.md`, supplied by the founder. The single long
`/services` page became a **hub** that routes, plus six **detail pages**
(`/services/website`, `/software`, `/app`, `/grow`, `/automate`, `/support`).

**One data file.** Every service name, price, feature and FAQ is in
`src/data/services.js`. The hub, detail pages, contact form, JSON-LD and
`llms.txt` all read from it, so a price changes in one place. Prices are stored
as numbers and formatted with Nepali grouping (`1,20,000`), so the display
string and the schema `Offer` can never disagree.

**Old links still work.** `/services#build`, `#grow`, `#automate` and `#support`
land on the matching group on the hub, because each group keeps that id. (A
fragment never reaches the server, so no server redirect could do this anyway.)
Old contact links with `?need=portfolio` or `?need=business-software` map to
`landing` and `software`.

**Contact form gained a "Service" list.** The spec requires every `?need=` value
to exist as an option and be pre-selected. The server validates it against the
same list, and the enquiry email names the service.

**The 14-day support conflict.** The spec gives landing pages 14 days of support
while the site-wide commitment said "30 days support on every project". Both
cannot be true, so the commitment now states the real figures: 30 days on
websites and stores, 60 on software and apps, 14 on a landing page.

**Icons: drawn by code, not by hand.** The thirteen isometric icons are built at
build time by `src/lib/icons.js` from boxes on one isometric grid, so the
perspective and depth are identical across all of them by construction. About
1 KB of inline SVG each; no image requests.

**3D motion: CSS tilt, and no Three.js.** Cards tilt up to 6 degrees toward the
pointer (about 20 lines of inline script setting two CSS variables; mouse and
trackpad only) and the icon lifts 8px over a shadow that shrinks. Transform and
opacity only. The optional Three.js hero was **dropped**: the smallest useful
Three.js build is well over the ~40 KB ceiling the spec set for it, and it would
compete with the LCP element on the hub. Thirteen consistent isometric icons with
a restrained tilt read as more finished than a heavy canvas. Reduced motion turns
off the tilt, the lift and the scroll settle.

**Checked:** Lighthouse mobile 100/100/100/100 on the hub and all six detail
pages (LCP 1.5–1.7s, CLS 0, TBT 0 ms; the accessibility score is axe-core);
every internal link and anchor resolves; every `?need=` has a matching option; Google's Rich Results Test on the deployed preview found valid Breadcrumbs, Local business and Organisation (its one optional warning, `priceRange`, is now set from the price list);
every title is at most 60 characters and every description at most 155; every
character on the pages is inside the subset fonts.

**Not in the project:** the spec refers to `CLAUDE.md` and to `logo-header-*`
brand files. Neither exists here, so the budgets in the spec itself were used, and
the footer now inlines the same generated `logo-full-white.svg` lockup the header
system uses (the stray copy in `public/brand/` was deleted). The footer email bug
in §0 had already been fixed.

## Company voice and the Build pages redesign (founder's direction)

**Vocabulary.** The founder asked that the site read as a company and a team, not
a freelancer. "Free call" and "free review" were retired everywhere (25 places).
The standard terms now are:

| Retired | Standard |
|---|---|
| Free scoping call | Consultation (at no cost, no obligation) |
| Book a free scoping call | Schedule a consultation |
| Get a quote for a … | Request a proposal |
| Free process review | Process assessment |
| Quoted after a free call | By proposal |

Casual phrasing and contractions in headings and descriptions were rewritten
("Drowning in messages?" → "More messages than your team can answer?", "We don't
disappear after launch" → "We stay accountable after launch"). The honesty stays;
only the register changed.

**Design of /services/website, /software and /app.** They had become long single
columns of equal-weight lists. Each now follows one structure:

1. A hero with an isometric scene, a kicker ("Build — Website"), the answer-first
   block and two actions, closed by a four-item facts strip.
2. Capabilities as icon tiles; deliverables as titled groups (19 flat bullets
   became four groups of four or five); a comparison table where a buyer is
   choosing (off-the-shelf vs custom; progressive web app vs native); the
   delivery process as numbered stages; the FAQ as an accordion.

**The signature.** Every Build page heading ends in the amber square, as the home
hero does, and its words drop into place on load; section headings do the same as
they scroll in. The hero scene assembles piece by piece, once. It is the "building"
metaphor, and the motion language the site already had (things settling into
place). Transform and opacity only, never looped, off under reduced motion and in
print. Lighthouse mobile: 99–100 on all three pages, LCP 1.7–1.8 s, CLS 0.

**Icons.** Eight concept icons (lock, coins, sheet, users, store, calendar, gauge,
launch) and three scenes were added to `src/lib/icons.js`, drawn on the same
isometric grid as the thirteen service icons, so the family is consistent.

### Delivery models (founder's direction)

Each Build page now has a "Delivery models" section after its own delivery
stages. It states the principle first — no project is forced into one model; the
model follows the client's requirements, the certainty needed on cost and how
the product will change, and the proposal names it — then gives the three
deciding factors and seven models as a native `<details>` accordion: Waterfall,
Iterative Waterfall, Incremental, Agile (Scrum), Prototyping, V-Model and Kanban
(the last for work after launch). Each shows its phases, how it works, what it
suits and how it is priced and approved.

## Two bugs found after the first deploy

**Unknown URLs returned the home page with HTTP 200.** Cloudflare Pages falls
back to `index.html` when a project has no `404.html`, which is correct for a
single-page app and wrong for this site: every mistyped or stale URL became an
indexable duplicate of the home page — a soft 404, and one Google penalises.

Two changes fixed it. A real `src/pages/404.astro` (noindex, lists all five
pages, offers WhatsApp), and `dist/_routes.json` limiting the Pages Function to
`/api/*`. The second one is the part that actually mattered: with Functions
deployed and no routes file, the worker is invoked for *every* request and the
static asset server's 404 handling never runs. Verified live — `/anything-else`
now returns 404, the five real pages return 200, and `POST /api/contact` still
reaches the Function.

**`_headers` rules append rather than override on Pages.** Covered under
Security above; it had been silently costing the fonts and hashed assets their
long-lived caching.
